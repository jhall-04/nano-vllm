# Checkpoint 1 Notes
The initial stages of development have been going well. To start the layout of this project I began with a very simple skeleton. That skeleton served to ensure the basics of my testing were in good order and that everything was ready for the implementation of any LLM Calls.

## The Start
Something I wanted to get right early was testing and logging. Why build if you have no way to verify that it is correct? The first test I implemented was essentially a load tester. By specifying a duration and number of queries per second, the load tester would bombard the initially blank generate API endpoint with "hello world" requests. An issue I quickly noticed when checking the logs was that API requests were only being made once the previous request had been completed. Having realized this, I knew the solution would be to send each API call as an async task maintained in a list alongside all other tasks. Additionally, to ensure no blocks were occurring due to `sleep(1/qps)` for each call, the sleep was moved to the asyncio version, ensuring that the number of calls to the API was closer to the load we wanted to test. Once I was sure that this initial test and the associated logging were correct, it was time to move on to generation.

## Generation
For this project, I used Qwen/Qwen2.5-0.5B-Instruct as my primary model. It is lightweight enough to run on both my desktop and laptop at the speeds needed for these simulated loads to be interesting, while still allowing me to iterate and see results without extended wait times. To begin, I started with the generic demo provided on the Hugging Face page for Qwen. This allowed me to ensure I had the necessary packages and that the model was running smoothly. Once I had verified this, I created an engine class that will serve as the backend interface while I iterate between various inference services and query management methods. Now that I finally had the engine running and could make simple calls through the API, it was time to check the load tests. As I scanned across various QPS values, I found the load tester would crash at 8 queries per second. After some investigation, I found that this was because generation in the engine was being done synchronously, so a query could hold the loop until generation completed. On my system, the load eventually became too heavy and caused the system to crash while waiting for that one call to release the hold.

## Locking
Once I realized the issue with the load testing, I knew I needed a way to limit access without locking up. As the requests piled up, the system needed a way to prevent the loop from locking while also ensuring requests completed as soon as possible. For this, I dispatched the synchronous generation to a thread while using a semaphore to ensure only one request was being generated at a time.

## Golden Set
Now that the early issues I faced with basic generation were resolved, it was time to work on a golden set. This ensures that, as the system evolves and changes across various inference methods, the output has a consistent baseline for comparison. It also ensures that future outputs remain consistent with prior results and that future generations do not stray from the baselines set with v1. To create the set, I had Claude generate a few sample prompts with various expectations and reasoning. These tests all occur with greedy sampling to make repeated runs deterministic. Once I had this set of prompts and decoding parameters, I ran an initial test with two runs, verifying that the output was the same both times. Once consistency was verified, the responses were added to the golden set as the standard responses for all future iterations to be held against. With that completed, I wrapped up today's work.

## Next Goals
Viewing the logs, I can see that as requests stack up, the backlog of queries grows, resulting in significantly higher wait times for later requests, especially as the number of queries per second increases. From this, I have two primary goals for the next iterations. First, I want to calculate concrete statistics on my first benchmark of the naive approach to establish a baseline for measuring how significant future improvements are. Second, I want to work on the issues related to queue times and explore how scheduling and batching can resolve the extreme delays I am seeing at high loads.
